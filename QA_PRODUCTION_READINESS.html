Production Readiness Assessment

Risk-based validation of functional correctness, edge cases, safety controls, model quality, latency, portability, and operational readiness.

NO-GO FOR PRODUCTION
Assessment date: 2026-10-06 Scope: CLI, agent, evaluator, artifacts, packaging Environment: Windows · Python 3.11

Decision: The repository is a credible proof of concept, but it is not ready for a customer-facing production release. It should be limited to a controlled demo with human review of generated SQL and results.

Primary blockers

  • Retired default model The configured Kimi K2.6 default is documented as retired after September 25, 2026.
  • Unbounded execution and output No SQL deadline, cancellation, row cap, byte cap, or safe pagination.
  • Silent semantic errors Executable but incorrect SQL bypasses repair and is returned confidently.
  • Insufficient generalization evidence Only ten public development questions from one known schema were measured.
  • Database portability mismatch The database can change, but documentation remains tied to the bundled financial schema.
  • No production load evidence Concurrency, rate limits, sustained throughput, and isolation remain untested.

Required release gates

  1. Select a currently supported model and pass a clean default-path smoke test.
  2. Enforce model and SQL deadlines, cancellation, maximum rows, maximum bytes, and safe pagination.
  3. Use a real SQL parser plus SQLite authorizer/progress controls instead of prefix and semicolon checks alone.
  4. Discover and document each selected database independently, filtered by the caller's permissions.
  5. Add semantic validation, abstention/clarification, and a quality fallback.
  6. Establish a frozen held-out suite covering unseen schemas, paraphrases, ambiguity, and adversarial prompts.
  7. Demonstrate production-like load with P50/P95/P99, error rate, cost, cache-state, and rate-limit measurements.
  8. Add structured, redacted telemetry and auditable query records.
  9. Prove clean dependency restoration and tests on every supported OS.

Suggested pilot acceptance criteria

  • At least 98% execution accuracy on representative held-out queries
  • Zero dangerous or unauthorized query escapes
  • Explicitly bounded silent wrong-answer rate with abstention measured separately
  • P50 under 3 seconds plus an agreed P95 under concurrent load
  • 100% enforcement of row, byte, and execution-time limits
  • No cross-user context leakage under concurrency
  • Reproducible clean install and a fully passing automated release suite
  • Auditable, redacted telemetry for every production query
